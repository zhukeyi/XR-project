# 模块对齐与版本策略

版本：1.0（2026-11-10，对应仓库 v0.1）
适用范围：`mecha_render/`（M1）与 `PICO_Mecha_Starter/`（M2）的日常协作

## 1 这份文档解决什么问题

两个模块会**各自演进**：M1 在造型与渲染上快速试错，M2 在交互与性能上快速试错。若没有约定，会出现三种典型故障：

1. **尺度漂移**：一边改比例，另一边不知道，合模时才发现对不上。（当前正在发生，见 `00_项目状态_v0.1.md` §4）
2. **回滚污染**：为了撤掉 M1 的一个坏改动，把 M2 的未完成工作一起回退了。
3. **产物入库**：把 2.4 GB 的 `Library/` 提交上去，之后每次 clone 都痛苦。

本文用三条规则分别封死：**接口唯一、提交分域、产物不入库**。

## 2 模块边界

| 事项 | M1 | M2 | 判定规则 |
|---|---|---|---|
| 几何、比例、枢轴命名 | 拥有 | 消费 | 谁产生数据谁拥有 |
| 尺寸数值 | 提出并论证 | 评审并写入契约 | 数值只能存在契约里，不能只活在脚本里 |
| glTF / FBX 导出 | 拥有 | 消费 | 导出设置（scale=1、Y-up、三角化）由 M1 保证 |
| 刚体绑定、VAT、材质实例 | 提供源 | 拥有 | 绑定是引擎侧行为 |
| 座舱交互、战斗、性能 | — | 拥有 | M1 不碰 |
| 宣传片 | 拥有 | — | — |

**禁止事项**：M2 不得在 Unity 里直接改 M1 导出的网格；M1 不得为了让 Unity 好看而在导出时做非契约的缩放。二者的例外都必须走 §5 的变更流程。

## 3 接口三件套

跨模块只允许这三样东西流动，其余一律视为耦合：

| 接口 | 载体 | 唯一真源 | 变更成本 |
|---|---|---|---|
| 尺寸与枢轴 | `PICO_Mecha_Starter/Contracts/尺寸与接口契约表.md` + `contract.json` | `MechaContract.cs` 的字段 → 编辑器菜单导出 | 高（升契约版本） |
| 资产 | `*.glb` / `*.fbx` | M1 导出脚本 | 中 |
| 命名 | 枢轴名、材质名 | 契约 §2.2 清单 | 低但必须一致 |

契约的机器可读副本 `contract.json` **当前缺失**，属 P0 待补。补上之后，M1 的导出脚本可以直接读它做自检，不必人工核对。

## 4 版本策略

三层版本，互不阻塞：

| 层 | 形式 | 谁升 | 例 |
|---|---|---|---|
| 仓库 | `vX.Y`，Git tag | 集成点达成时 | `v0.1` |
| 模块 | `M1-vX.Y` / `M2-vX.Y`，记录在本文 §7 | 模块自身里程碑 | `M1-v0.2` |
| 契约 | `vX.Y`，写在契约文件头 | 任何尺寸/枢轴/命名变更 | `v1.1 → v1.2` |

规则：
- **契约版本是硬门**。契约不动，两模块可自由前进；契约一动，两模块必须同步声明"兼容 / 需迁移"。
- 模块版本不等于仓库版本。M1 可能到 `M1-v0.5` 而仓库仍在 `v0.2`。
- 每个仓库 tag 必须附带一份可运行的组合（能导出资产 + 能开 Unity 工程）。

## 5 提交约定（决定能否干净回滚）

提交信息必须带域前缀，否则无法按模块筛选与回退：

```
[M1] 导出 7.930 m glTF，补齐 18 枢轴
[M2] 白盒按契约 v1.2 重建
[contract] v1.1 -> v1.2: 总高 18.20 -> 7.930
[docs] 新增资产交付规格
[pm] 状态盘点与对齐策略
```

配套命令：
- 看某模块历史：`git log --oneline --grep="\[M1\]"`
- 单模块回滚：`git revert <sha> -- mecha_render/`
- 契约回退：`git revert <sha> -- PICO_Mecha_Starter/Contracts/ PICO_Mecha_Starter/Assets/_Project/Scripts/Core/MechaContract.cs`

**禁止** `git reset --hard` 到共享分支。回滚一律用 `revert`，因为 `revert` 保留历史，能回答"为什么撤"。

## 6 改契约的六步流程

1. 在 `03_决策日志.md` 记一条 ADR（提议状态），写清动机与影响面。
2. 改 `MechaContract.cs` 字段（39 float + 7 Vector3，改哪些写进 ADR）。
3. 菜单执行「契约/导出 JSON」，生成 `contract.json` 与 Markdown。
4. M2 重建白盒，跑 33 条自检；尺寸相关项必须全绿。
5. M1 重新导出资产，跑尺寸断言（总高 ±0.02 m、脚底 y≈0、18 枢轴齐全）。
6. 提交信息写 `[contract] vX.Y -> vX.Z`，仓库打 tag。

## 8 每次任务的开合仪式

你说"改这个"或"回滚这个"时，按此执行，避免两个模块各自漂移：

**开**（接任务时）
1. 判断落在哪个域（M1 / M2 / 契约 / 文档）。
2. 判断是否触碰契约（尺寸、枢轴、命名、路径）。
3. 触碰则先写 ADR，不触碰直接做。

**合**（交付时）
1. 跑该域的自检（M1：尺寸断言；M2：33 条合规）。
2. 更新 `00_项目状态` 的对应行。
3. 带域前缀提交。
4. 若动过契约，两模块都更新 §7 版本记录。

## 9 忽略规则

`out/`、`frames/`、`Library/`、`ref_assets/`、`*.apk`、`*.mvfrm` 一律不入库，原因写在 `.gitignore` 注释里。**其中 `ref_assets/` 是版权原因，不是体积原因**——它含第三方高达模型，只作内部度量参照，不得进入任何公开仓库。
