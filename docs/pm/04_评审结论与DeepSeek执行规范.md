# XR-project 评审结论与 DeepSeek Blender 执行规范

版本：1.0  
日期：2026-11-11  
适用项目：XR-project / 《钢脊》PICO Space Program 2026 OpenXR 赛道  
决策状态：已确认机体总高 7.930 m  
用途：作为剧情设计、Blender 建模、刚性绑定和 Unity 集成的共同执行依据

---

## 1. 已确认决策

1. 机体包围盒总高固定为 **7.930 m**。此决定覆盖旧契约、旧白盒和旧导出流程中的 18.20 m 数值。
2. 最终运行目标为 PICO OpenXR 全沉浸体验。当前阶段不以 Rokid AR 或其他 AR 平台适配为交付目标。
3. 按用户指定的分工，由 Codex 与 Kimi 协助形成唯一的体验台本和制作规格；DeepSeek 按任务单执行 Blender 建模、绑定和导出。DeepSeek 不通过聊天记录猜测尺寸或自行改变接口。
4. Blender 中的模块化结构是制作组织方式；Unity 接收的资产必须保留契约规定的总坐标、层级、挂点和骨骼语义。
5. 本文是项目评审与制作执行规范，不代表模型或游戏已经通过 Blender、Unity 或 PICO 真机验收。代码和场景仍需按下文更新。

## 2. 项目评审摘要

仓库已有可继续使用的基础：M1/M2 模块边界、Python 程序化灰模、GLB 层级导出工具、Unity 尺寸契约、白盒生成器和静态合规检查。M1 负责资产来源，M2 负责引擎内交互，这种分工适合并行制作。

当前版本仍是规格和白盒阶段，不是已完成的 OpenXR 作品。状态盘点列出的主要工作包括尺寸迁移、真实资产交付、座舱交互、战斗和设备性能验收。原计划的登机、启动、CIC 简报、弹射、驾驶、射击、近战、返航和结算覆盖了多个独立玩法环节；应先做出一段有始有终、能在头显中体验的单次任务，再扩充其他环节。

### 2.1 P0：7.930 m 尚未成为全仓唯一尺寸

现有 M1 灰模和资产交付规格采用 7.930 m；Unity 的 MechaContract 默认值以及部分白盒尺寸仍采用 18.20 m。GLB 导出器的 normalize 路径也把目标高度写成 18.20 m。旧数据可能使导入资产被缩放 2.3 倍。

**执行要求：**在新资产开始制作前，契约负责人必须发布新的契约版本，并同步更新：

- MechaContract.cs 中总高、分件高度、舱体位置、挂点和相关派生值；
- 人读契约表和由编辑器菜单生成的 contract.json；
- 白盒生成器、白盒场景和尺寸自检；
- GLB 导出脚本中的旧 18.20 m normalize 路径；
- 资产文件名、审计报告和 Unity 导入检查。

禁止把旧契约的 39 个浮点字段和 7 个 Vector3 统一乘以 7.930/18.20。舱内空间必须维持人类可用尺度，外部机体尺寸、座舱离地高度和机械分件要重新解算。已有资料中的座舱净空约 1.6 × 2.0 × 2.2 m 可作为设计输入；座椅眼位和挂点位置须根据新外形重定，不能沿用旧的 11 m 级高度。

### 2.2 P0：当前 GLB 导出器不等于刚性绑定交付

现有 export_gltf.py 从 Python 节点树写出 mesh 和层级变换，没有写 glTF skin、joints 或 vertex weights。资产交付规格要求的是顶点 100% 归属一个骨骼，并由单个 SkinnedMeshRenderer 承载多材质 submesh。两者是不同的交付形式。

**执行要求：**最终绑定资产使用 Blender 的 Armature 和 glTF 导出链路；现有 Python GLB 生成器只作为灰模、对照或暂时代码，不能被当成已输出蒙皮资产。第一件事不是做全机，而是完成一个带铰链或肩关节的小型端到端样件，确认 Blender → GLB → Unity 能保留骨架、权重、枢轴、轴向和尺寸。

若 Unity 导入器不能按既有规格生成一个 SkinnedMeshRenderer，就记录实测结果并提交规格变更；不得通过拆掉骨骼、丢失枢轴或在 Unity 中手工缩放来假装通过。

### 2.3 P1：现有比赛自检不是运行性能验收

ContestComplianceValidator 检查当前打开的场景，并用网格面数、材质和子网格数估算预算。脚本注释指出 Draw Call 估算没有计入阴影与后处理 pass。它没有测量头显中的稳定帧时间，也不会覆盖未加载的运行时生成对象。

**执行要求：**把静态检查当作早期门禁；最终帧率、舒适性、手柄响应、OpenXR 启动和真实 draw call 必须在目标设备或比赛认可的目标运行环境验证。不得把“自检 FAIL=0”写成“90 Hz 已验证”。

### 2.4 P1：制作分工还缺 Unity 集成与验收责任

剧情和 Blender 执行有人负责，不代表 OpenXR 项目自动集成完成。每个资产任务都必须有明确的 Unity 集成负责人，负责导入、Prefab、场景交互、打包和设备验收。用户可以指定自己或 Codex 协助，但任务单必须写明负责人；DeepSeek 的 Blender 交付不视为游戏功能完成。

## 3. 目标体验与第一版范围

### 3.1 第一版垂直切片

第一版只要求完成一段完整任务闭环：

1. 玩家坐在驾驶舱内，能自然看到机体内部和舱外尺度；
2. 玩家操作一个明确的启动或确认控件；
3. 舱门关闭或出击过程给出清晰的视觉、声音和身体运动反馈；
4. 玩家完成一次主要操作，例如瞄准并攻击一个目标，或保护一个目标；
5. 任务结果清晰，玩家能返回或结束任务。

第一版暂缓：完整步行登机、复杂 CIC 简报、多种敌人、完整近战系统、全套返航着舰模拟、跨设备 AR 和大量可破坏物。若这些环节只为表达剧情，可用短对白、动画或镜头转场，不要为了台本完整而实现多套未验证的交互系统。

### 3.2 Codex 与 Kimi 的台本交付格式

两边可以分别提出创意，最终必须合并成一个获批版本。给 DeepSeek 和 Unity 实现方的输入不能是互相矛盾的聊天记录。

每个体验节拍至少包含：

| 字段 | 内容 |
|---|---|
| Beat ID | 稳定编号，例如 B01 |
| 玩家状态 | 坐姿、手柄状态、可活动范围 |
| 玩家动作 | 玩家实际需要做的输入 |
| 触发条件 | 何时开始、何时结束 |
| 画面目标 | 玩家主要看向何处、关键物件在哪里 |
| 声音与触觉 | 提示来源、方向、时机、强弱 |
| 系统响应 | 交互成功后游戏发生什么 |
| 失败/中断处理 | 松手、误操作、追踪丢失、应用暂停时如何恢复 |
| 资产依赖 | 需要的模块、骨骼、碰撞体、动画和材质 |
| 验收条件 | 能复现、能观察、能判定通过或失败 |

台本中要标记内容是“玩家可操作”还是“过场表现”。DeepSeek 只根据定稿节拍制作被明确点名的资产，不自行增加武器、骨骼、额外剧情或交互。

## 4. Blender 生产规则

### 4.1 源文件与模块边界

以一个 Blender 主文件保存完整机体与统一骨架；按 Collection 或明确的模块层级组织部件。模块可以独立隐藏、替换和审查，但不得各自建立互不一致的世界原点、机体高度或坐标方向。

推荐模块：

| 模块 ID | 内容 | 第一版优先级 |
|---|---|---|
| M00_ROOT | MECH_ROOT、整机坐标、公共骨架和辅助节点 | P0 |
| M01_COCKPIT | 座舱壳、内舱净空、SeatAnchor、ChestSocket、舱门及铰链 | P0 |
| M02_TORSO | 胸、腰、背包连接结构 | P0 |
| M03_ARM_L / M04_ARM_R | 肩、上臂、肘、前臂、手部、武器挂点 | 按第一版交互决定 |
| M05_LEG_L / M06_LEG_R | 髋、腿、膝、踝、脚底 | P1 |
| M07_HEAD | 头部、传感器、天线 | P1 |
| M08_BACKPACK | 背部设备和喷口 | P1 |
| M09_WEAPON | 第一版实际使用的一种武器 | P0，仅做一种 |
| M10_TARGET | 一种无人机或任务目标 | P0，仅做一种 |

模块内部统一使用“灰盒 → 枢轴确认 → 刚性绑定 → 导出 → Unity 导入验收 → 细节”的顺序。头部、腰部、手掌等贴近视点的物件应较早做尺寸和碰撞测试；不要先花时间制作全机微小面板、管线和发光细节。

### 4.2 坐标、单位和变换

导出资产必须满足下列契约：

- 1 Blender unit 表示 1 m；Unity 中 1 unit 也表示 1 m；
- 最终 GLB 为 Y-up，机体正面为 +Z；
- Blender 内部 Z-up 到导出 Y-up 的转换只能发生一次；
- 机体脚底最低点 y = 0 ± 0.005 m；
- 整机包围盒高度 7.930 ± 0.020 m；
- Unity 导入 Scale 为 (1,1,1)，禁止用 Inspector 缩放修正错误；
- 网格顶点保持在所属部件的局部空间，节点变换表达部件位置和旋转；
- 保留父子层级，不要在导出前把所有网格应用到世界坐标或合并成无语义的一块；
- 移动部件的原点放在真实铰链或旋转轴上；旋转测试后再开始贴图。

### 4.3 固定命名

以下节点名区分大小写，不得翻译、加前后缀或重复：

- MECH_ROOT
- hips、chest、head、backpack
- shoulder_L、shoulder_R
- elbow_L、elbow_R
- hip_L、hip_R
- knee_L、knee_R
- ankle_L、ankle_R
- hatch_hinge_L、hatch_hinge_R
- SeatAnchor、ChestSocket

注意：上述列表中 SeatAnchor 和 ChestSocket 是辅助挂点，不是变形骨骼。它们不得被计入权重骨骼数量。现有资产规格把 16 个关节/铰链节点与两个辅助挂点合称为 18 个具名枢轴；交付 JSON 应分别报告“骨骼”和“辅助节点”，避免数量口径误导。

当前规格没有完整定义左右腕、左手交互、武器接口和足部机构等所有可能的骨骼。如果第一版需要 wrist_L、wrist_R 或 WeaponSocket 等节点，先由契约负责人提出并批准，再更新 M1/M2 契约版本。DeepSeek 不可自行造名，也不可让 Unity 脚本依赖未登记的节点。

### 4.4 刚性绑定规则

“刚体绑定”在本项目指硬表面 rigid skinning，不是给每块甲片添加 Unity Rigidbody。

- 机体外壳、装甲、头部和背包等硬表面顶点权重必须 100% 归属一个骨骼；
- 不允许两骨混合权重、形态键和用于硬表面的变形骨；
- 允许例外的柔性件仅限液压管、线束、安全带、柔性护套；每个例外要在清单中说明；
- 座舱门、武器和其他独立可动件使用登记过的铰链或挂点；
- 只给确实需要物理模拟的游戏物件使用 Rigidbody，例如弹体或可拾取物；机甲装甲零件不要各自做物理刚体；
- 在 Blender 中对照静止姿势和关节极限检查接缝、穿插、空洞和错误父子关系；
- Unity 中测试骨骼动画和碰撞前，先确认 GLB 导入的骨骼数量、名字、bind pose 和 Skin 权重均符合报告。

现行交付规格期望最终机体为一个 SkinnedMeshRenderer、多个材质 submesh。先用单个小模块验证这一点能被 Blender GLB 导出器和 Unity 导入器保留，再套用到全机。若导入结果只能生成多个 Renderer，提交方案和性能对比，由契约负责人决定是否修导出或修规格。

## 5. 几何与移动端预算

沿用资产交付规格中的初始预算，作为制作上限而非真机性能结论：

| 资产 | 初始三角面预算 | 材质预算 | 说明 |
|---|---:|---:|---|
| 机体 LOD0 | 80k–150k | ≤ 8 | 机体总预算 |
| 机体 LOD1 / LOD2 | LOD0 的约 30% / 10% | 共用 | 只在实际视距需要时制作 |
| 座舱内景 | 50k–80k | ≤ 6 | 贴近视点，优先保轮廓和操作可读性 |
| 无人机单型 | 20k–30k | ≤ 3 | 同屏数量与帧率须真机验证 |

- 机体优先共用材质、Trim Sheet 和 Atlas，少做材质槽；贴图按资产规格使用 PBR Metallic/Roughness。
- 座舱按钮必须以可操作性建模；不能被玩家触及的表面不制作过量细节。
- 需要碰撞的部位提供简化碰撞体，命名前缀使用 COL_；禁止把高面数渲染网格直接当作全机动态 MeshCollider。
- 不做未被第一版体验使用的第二把武器、额外挂载和微缩饰件。
- 如果场景需要同屏 40 架无人机，先用灰模验证可见数量、遮挡、draw call 和运行帧时间；VAT 是候选方案，不是已经验证的性能结论。

## 6. DeepSeek 单模块任务模板

每次只提交一个模块或一个明确的修复任务。任务提示中提供当前定稿的台本节拍、契约文件和模块验收表。

| 项目 | DeepSeek 必须收到的内容 |
|---|---|
| Task ID | 模块编号和版本 |
| 目标 | 玩家为什么会看到或操作这个模块 |
| 输入 | 当前 master .blend、契约版本、参考正侧视图、需遵守的节拍 ID |
| 尺寸 | 总高/局部包围盒、单位和脚底/座椅基准 |
| 枢轴 | 节点名、父节点、坐标、旋转轴和允许角度 |
| 材质/几何预算 | 三角面、材质、贴图、碰撞预算 |
| 输出 | 更新后的 .blend、复现脚本（如有）、GLB、审计 JSON 和简短差异说明 |
| 验收 | 本规范第 7 节中此模块的所有项目 |
| 停止条件 | 发现契约缺项、比例冲突、骨骼缺失或预算冲突时停止，不自行猜测 |

每次执行后 DeepSeek 应说明：改了哪些对象；新旧包围盒；修改了哪些骨骼/枢轴；新增材质与面数；GLB 中发现的节点和皮肤；未通过的检查。不得只返回截图或口头说明。

## 7. 每个模块的验收门

### A. Blender 源文件门

- 对象位于正确 Collection，名称符合契约；
- 无 Cube、Camera、Light 等默认游离物体进入交付；
- 部件变换和父级关系可解释，非均匀缩放为零；
- 枢轴位置与轴方向正确，铰链至少能在 Blender 中往返旋转；
- 记录模块局部包围盒、三角面、材质和纹理清单；
- .blend 文件可重新打开并复现导出，不依赖个人临时目录中的隐藏文件。

### B. GLB 导出门

必须输出 GLB 2.0 和同版本 JSON 审计报告。报告至少包含：

- 契约版本、资产版本、导出器版本；
- 全局包围盒、脚底位置和是否达到 7.930 m；
- 主要部件和所有登记的骨骼/辅助节点名称；
- skin 数量、joint 列表、每顶点权重数量分布；
- 节点总数、mesh 数、材料数、三角面数和文件大小；
- 游离物体和重复节点；
- 坐标轴、单位、根节点变换和异常 scale；
- 验收结果 PASS/FAIL 和每项失败原因。

### C. Unity 导入门

每次合并新 GLB 后，在干净的测试场景验证：

- Unity Import Scale = 1；模型正面朝 +Z、上方为 +Y；
- 总高 7.930 ± 0.020 m，脚底 y = 0 ± 0.005 m；
- 所有枢轴名、父子层级、座舱和武器挂点都存在；
- 旋转舱门、手臂和武器时只带动预期部件，不带动根节点或整机；
- 材质、法线、透明度、阴影和双眼渲染正常；
- 动态交互对象使用简化碰撞体，没有多余 Rigidbody；
- 导入和运行过程中没有静默重缩放或坐标补偿。

单模块验收失败就退回 Blender 修正，不能在 Unity 内临时移动节点或缩放 Transform 来掩盖资产错误。

## 8. Unity / OpenXR 最小运行门

进入高细节资产制作前，先在目标设备或认可模拟环境跑通：

1. OpenXR 应用可启动，单个 XR Origin、相机和 Audio Listener 配置正确；
2. 玩家头部移动能改变视点；至少一个手柄位姿可读；
3. 一个按钮或驾驶杆可由射线/抓取操作并产生可观察的结果；
4. 应用暂停、恢复和离开场景时没有卡死或状态丢失；
5. 体验任务可从开始运行到结束，不要求开发者在编辑器里手动补状态；
6. 在目标设备记录 CPU/GPU frame time、实际刷新率、渲染分辨率、draw call、内存和发热；
7. 手柄操作和视点运动通过舒适性检查；加速与转向保留舒缓选项。

PICO 开发指南建议先验证头显姿态、控制器、射线和一个交互物件，再增加高级能力；并要求记录 Unity、SDK、插件、设备和系统版本，最终在实体设备上做性能验证。Unity 版本达到最低线并不等于任意 SDK 组合都已验证。
