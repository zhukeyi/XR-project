## 2 三条 P0 的核实结果（附证据）

### 2.1 ✅ 属实：`export_gltf.py` 硬编码 18.20

| 位置 | 代码 |
|---|---|
| `mecha_render/tools/export_gltf.py:329` | `s = 18.20 / H` |
| 同文件 `:340` | `'normalized_to_height': 18.20,` |
| 同文件 `:489` | 打印文本同样写死 18.20 |

**这是全仓最危险的一行**：只要有人跑 `--normalize`，7.930 m 的模型会被静默放大 2.296 倍，且**审计报告会显示"已归一化到 18.20"而不报错**。

### 2.2 ✅ 属实：导出器不产 skin —— **这一条是我方规格的内在矛盾**

| 检查项 | 结果 |
|---|---|
| `export_gltf.py` 中 `skin` / `JOINTS_0` / `WEIGHTS_0` / `joints` / `Armature` 出现次数 | **0** |
| `02_资产交付规格` 要求 | "顶点 100% 归属单骨、由单一 SkinnedMeshRenderer 承载多材质 submesh" |
| `17.4 A1` 要求 | "把 `s2_graybox.py` 的节点树适配到 `export_gltf.py` 的序列化格式，导出 `mecha_793.glb`" |

**矛盾在于：我指定的工具，做不出我要求的资产。** 这是 04 抓得最准的一条，比它的两条 P0 都更重要——因为它意味着我写的两份文档（02 规格、17.4 A1）互相不成立。

### 2.3 ✅ 属实：Unity 侧仍是 18.20 全套旧值

| 位置 | 值 |
|---|---|
| `MechaContract.cs:20` | `totalHeight = 18.20f` |
| 同文件 `:26` | `chestSocketY = 12.60f` |
| 同文件 `:200` | 断言硬编码 "契约 11.40" |
| 同文件 `:203` | 断言硬编码 "契约 11.55" |
| 同文件 `:269` | 天线 17.60–18.20 |

**注意 `:200` 与 `:203`**：这两处不是字段而是**硬编码断言值**。即使把字段改成 7.930，这两条断言仍会按旧值判定，产生"改了却报错"的假故障。**04 没有点出这一层，我在 §4.2 补上。**

## 3 我方必须承认的三处错误

### 3.1 排期假设错误（最严重）

**实际赛程（已核实三个独立来源：映维网、VRAR星球、新浪）**：

| 节点 | 日期 |
|---|---|
| 报名开启 | 10/29 |

| **报名与提交同时关闭（最终版本锁定）** | **12/19 09:00** |

| 决赛入围公布 | 12/24 09:00 |
| 线下决赛路演（北京大钟寺 F3） | 12/26 |

赛道：三条，我方属 **OpenXR →「最佳沉浸内容创作」**（2 组，每组 ¥20,000 + 1 台 PICO Space Pro）。

**这意味着我方多出 25 天。** 04 的 §9 判断正确。

### 3.2 「18 个枢轴」的口径混淆

我在 `02_资产交付规格` 写"18/18 具名枢轴"，把两类东西混为一谈：

| 类别 | 数量 | 说明 |
|---|---:|---|
| 变形/铰链骨骼 | **16** | hips/chest/head/backpack + shoulder×2 + elbow×2 + hip×2 + knee×2 + ankle×2 + hatch_hinge×2 |
| 辅助挂点（非骨骼） | **2** | SeatAnchor、ChestSocket |

**这两类在 Unity 侧的处理完全不同**：前者进 Animation/Skin，后者只作 Transform 锚点。合成"18 枢轴"会导致 Skin 骨骼计数虚高、权重审计误判。04 §4.3 的修正正确，采纳。

### 3.3 把两条交付路径混为一条

`17.4 A1` 说"导出 `out/film/mecha_793.glb`"用于宣传片，`02_资产交付规格` 要求同一资产必须带 skin。**这两件事的资产要求不同，我没有分开写。**

| 路径 | 动画方式 | 需要 skin 吗 | 理由 |
|---|---|---|---|
| **宣传片（预渲染）** | 节点 TRS 关键帧 | **不需要** | Blender 内逐帧改枢轴角度即可，渲染器不关心 skin |
| **引擎内（Unity）** | Armature + Skin | **必须** | SkinnedMeshRenderer 才能做运行时骨骼动画与绑定 |

**所以 04 §2.2 说"Python 生成器只作灰模"——对引擎路径完全正确，对宣传片路径则过度否定。** 宣传片用非蒙皮 GLB 是合法且更快的选择，`export_gltf.py` 在宣传片链路里**依然可用**。

这条区分很重要：它决定了 M1 是否要重写导出器。**答案是不必——只需把导出器定位从"交付资产"降级为"宣传片资产 + 灰模"，另开一条 Armature 链路给引擎。**

### 4.2 契约迁移的隐藏坑（04 未点出）

除字段值外，以下三处必须同步，否则出现"改了却报错"：

| 位置 | 问题 |
|---|---|
