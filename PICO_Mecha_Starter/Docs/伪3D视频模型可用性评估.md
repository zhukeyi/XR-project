# 伪 3D 视频模型在 PICO 项目中的可用性评估

日期：2026-11-08  
评估对象：`mecha_render`（《钢脊·白鸦》12 s 概念片所用的程序化模型）  
对照基线：`Contracts/尺寸与接口契约表.md` v1.1、`Docs/Unicorn包导入实测与差距评估.md`  
方法：**真导出 + 真测量**，脚本 `mecha_render/tools/export_obj_parts.py`，产物 `mecha_render/out/pico/`

---

## 1 结论先行

### 1.1 一句话

**形体可用、结构超预期、表面与座舱不可用。** 这是一个**合格的白盒（greybox）**，不是可交付的美术资产：它的关节树（265 节点 / 深度 8）比 Unicorn 包的 375 个平级对象**更适合做游戏资产**，但三角面只有 4,000（Unicorn 的 1.1%）、UV 是占位投影、贴图为零、座舱内景只有 2 件盒子。

换算成动作：**它能省掉"从零起形"的 20–30 小时，但省不掉后面的 132–194 小时。**

### 1.2 五级可用度

| 用途 | 判定 | 依据 |
|---|---|---|
| ① 提交材料里的「概念验证片 / 分镜动态稿」 | **可直接用** | 12 s 成片已交付，1280×720 / 24 fps / 有声，与参赛技术方案不冲突 |
| ② Unity 里的**白盒 / 临时占位体** | **改造 1 天后可用** | 需补一个 glTF 导出器（保层级）+ 材质临时替换 |
| ③ 正式美术资产的**几何底模** | **改造 132–194 小时后可用** | 座舱重做 + P0 三件精修 + UV + 贴图 |
| ④ 分件与枢轴的**契约对接底稿** | **可直接用** | 关节树位置已实测（见 §3.2），改名即可对齐 `Pivot_*` |
| ⑤ 直接交参赛的机体 | **不可用** | 4,000 三角 + 零贴图 + IP 风险（见 §7） |

### 1.3 一句话采购结论的修正

上一份《建模软件选型评估》推荐"程序化基底 + 手工精修"的 R2 路线，**这个模型就是那个"程序化基底"的现成坯料**——只是坯料的成熟度比预想的高（有层级、有铰链、有比例推导），但表面成熟度比预想的低（零 UV、零贴图）。

## 2 实测：这个工程里到底有什么

### 2.1 三个网格来源，只有一个能导出

|---|---|---|---|---|
| **影片模型**（全身） | `mecha_model.py` | 内存中的 265 节点树 | 原本不能，**本次已补导出器** | **可用** |
| S2 局部灰模 | `tools/s2_graybox.py` | `out/s2/s2_graybox.obj` | 能，但三角形汤 | 局部（头+胸+肩+一段上臂） |

关键发现：**全工程此前没有可用的导出路径**。`tools/s2_graybox.py:write_obj` 的写法是

```python
lines = ['o s2_upper']                      # 单一 object
for i in range(0, len(P_), 3):
    lines.append('f %d %d %d' % (i+1, i+2, i+3))   # 每三角形 3 个独立顶点
```

38 个零件在文件里塌成 1 个物体、无 `usemtl` / `vt` / `vn`。这不是疏忽，是当时只为了给渲染器看，不需要给引擎看。

## 3 逐维对照

### 3.1 尺寸链：六个数，两对两错

| 项 | 契约 | 实测 | 差 | 判定 |
|---|---:|---:|---:|---|
| 总高 | 18.20 | 19.021 | +0.82（+4.5%） | 缩放可修 |
| 肩宽（外缘） | 10.60 | **6.763** | **−3.84（−36%）** | **不可直接修**（见下） |
| 肩关节中心高 | 14.20 | 14.35 | +0.15 | 好 |
| **肩关节横向** | **±4.30** | **±2.201** | **−2.10（−49%）** | **造型取向冲突** |
| 上臂长（肩→肘） | 3.00 | 3.22 | +0.22 | 好 |
| 前臂长（肘→腕） | 3.20 | 3.04 | −0.16 | 好 |
| 脚底 | 0.00 | +0.160 | 悬空 16 cm | 一行代码 |
| 座舱坐面 | 11.55（眼位） | 12.60（`cockpit_seat`） | +1.05 | 见 §3.4 |

**为什么肩宽"不可直接修"**：手臂长度对得上（3.22 vs 3.00），但肩关节横向只有一半。这意味着两者的**造型取向不同**——

- 契约是「宽肩重装」：肩关节 ±4.30 悬在胸宽 6.40（半宽 3.20）之外 1.10 m，臂内缘 3.55 与胸缘留 0.35 缝；
- 模型是「收肩显腿长」：`PROP_DEFAULT` 里 `sx_chest=0.62` 把胸宽从 7.15 压到 4.43，肩关节随之收到 ±2.20，臂直接**压在胸侧**。

把模型横向拉宽 1.95 倍会把手臂拉成扁片。所以是**改契约还是改模型，必须二选一**，不能靠缩放糊过去。（`mecha_render/mecha_model.py` 的注释里记录了这次收窄的依据：肩宽/机高从 0.585 收到目标区间，是为了解决"一看就不厉害"的问题。）

| 契约枢轴 | 模型对应节点 | 实测世界坐标 | 判定 |
|---|---|---|---|
| `Pivot_Elbow_R` (0, 11.20, 0) | `elbow1` | (2.360, 11.127, −0.270) | **Y 差 0.07，可直接改名对接** |
| `Pivot_Wrist_R` (0, 8.00, 0) | `wrist` | (2.524, 8.091, −0.176) | Y 差 0.09 |
| `Pivot_Hatch_L/R` | `hatch_hinge±1` | (±0.570, 12.70, 1.672) | 轴向已实现 ±95° |

**结论**：7 个契约枢轴里 5 个已有现成节点且位置误差 < 0.1 m，2 个（操纵杆、节流阀）属于座舱内景，本来就没有。这是这个模型对项目最大的实际贡献——**枢轴不用重新量，改名就行**。

### 3.3 密度：全部严重不足

| 指标 | 模型 | 契约/目标 | Unicorn 基线 | 达标度 |
|---|---:|---:|---:|---:|
| 分件数 | **242** | ≥ 180 | 375 | **134%** ✓ |
| 三角面 | **3,976** | 350,000–500,000 | 377,328 | **1.1%** |
| 材质槽 | **11** | ≤ 30 | 25 | 44% |
| PBR 贴图 | **0** | 20（4 图集 × 5 图） | 81 | **0%** |
| UV | **0**（占位投影） | 4 张图集 | 有 | **0%** |
| 座舱语义件 | **2**（`cockpit_seat` + `cockpit_glow`） | 18 | 36 / 14 项 | **11%** |

单项平均三角面 = 3,976 ÷ 242 = **16.4 面/件**；Unicorn 是 1,006 面/件。**差 61 倍**。

最多面的一件是 `waist_tube` 36 三角（8 边圆柱）。也就是说：**这个模型里每一个零件都还是"块"，不是"零件"**。

| 应有（外包清单 A3） | 模型实际 |
|---|---|
| 座椅（坐垫 / 靠背 / 头枕） | `cockpit_seat` 一个 12 面盒子 |

| 左 / 右操纵台 | 无 |

| 节流阀 | 无 |
| 三窗框架 | 无（`cockpit_glow` 一块发光片代替） |

**11 件座舱相关分件，每件都是 12 三角的盒子。** 对比 Unicorn 的 36 件 / 14 项语义部件（三显示器、油门块、扶手、双脚踏、球形舱壳、滑轨）——这是 0 与 1 的差距，不是 60% 与 80% 的差距。

## 4 三个结构性障碍

### 4.1 OBJ 导出丢层级（**已解决**，见 §9）

OBJ 格式**没有父子关系**，只有平级的 `o` 组。所以 `mecha_parts.obj` 的 244 组进 Unity 后仍是 244 个平级对象——**和 Unicorn 包的问题一模一样**。

| 方案 | 状态 | 说明 |
|---|---|---|
| **glTF 2.0 导出** | **✅ 已完成并验证** | `tools/export_gltf.py`。原生支持节点层级；Blender 与多数引擎可直接读 |
| 写 FBX 7.x 二进制导出 | ✗ 不做 | 要 300–500 行。工程里 `tools/fbx_geo.py` 是**只读解析器**，逆着写成本高、且 FBX 规范不公开完整 |
| 靠名字重建层级 | ✗ 不可靠 | `hatch-1` 这类名字里没有父名，字符串推断必然错 |

**结论**：`mecha_parts.obj` 只解决"分件可分辨"；**层级问题由 `mecha_parts.glb` 解决**（§9）。

### 4.2 UV 是占位投影

`gfx/mesh.py` 第 160–162 行的注释写得很清楚：

```python
# UV 占位：用世界坐标的平面投影，M2 会替换为真实展开
uv = np.stack([[tp[j][0] * 0.15, tp[j][2] * 0.15] for j in range(3)])
```

即 `u = x × 0.15, v = z × 0.15`。这套 UV **必然重叠**（前后左右投影到同一平面），任何贴图上去都会拉伸错乱。

这是"从零做 UV"的工作量：4 张图集 × 20 个 UV 岛量级，12–18 小时（《建模软件选型评估》§3.1）。**不能省。**

### 4.3 材质是平色，不是 PBR

11 个材质全部是 `Mat(rgb, emissive, rim, spec)` 四个标量。渲染器 `gfx/shade.py` 用它们做赛璐璐量化着色——这在概念片里是对的（风格化），在 VR 里不够（玩家贴脸看会感到"塑料玩具"）。

Unicorn 的 25 个材质至少带 COL 贴图；我们的是**纯常数**。这决定了：**贴图必须重做，不能沿用**。

## 6 两条改造路线

### 6.1 路线 A：当白盒用（1 天）

| 步骤 | 工时 | 说明 |
|---|---:|---|
| 写 glTF 导出器 | 3–4 h | 保层级，产出 `.gltf` + `.bin` |
| Blender 导入 → 校正尺度（H→18.20、脚底→0） | 1 h | 等比缩放的代价是肩宽仍差 39%，**必须接受** |
| 导出 FBX 2020（含 Empty）→ Unity | 0.5 h | `ArtRoot` 下替换 |
| 材质临时替换为 URP/Lit + 单色 | 1 h | 11 个平色直接映射 |

**产物**：一个能跑、能进舱、能开门的白盒，视觉上是"灰色积木"。  
**用途**：让交互、座舱相机、枢轴动画、门 1 验收全部**先动起来**，不等美术。

这正是 `README.md` 里白盒管线的定位。**性价比最高的一条路，建议立刻做。**

### 6.2 路线 B：当几何底模重塑（132–194 h）

| 步骤 | 工时 | 可省吗 |
|---|---:|---|
| 导入 + 修层级 + 尺度重定向 | 5–6 h | 不可省 |
| **座舱 18 件重做**（贴脸精度） | 40–60 h | **不可省，这是最大缺口** |
| P0 三件（头 / 胸舱 / 座舱壳）细分 + 倒角 + 板缝 | 30–45 h | 可部分外包 |
| 非 P0 部位（腿 / 背包 / 腰裙）法线细节 | 15–20 h | 可欠配 |
| UV 4 张图集 | 12–18 h | 不可省 |
| 贴图 20 张（Substance） | 30–45 h | 可省一半（用智能材质） |
| **合计** | **132–194 h** | — |

对比《建模软件选型评估》§3.1 的"从零做"（194–291 h）——**这个模型省掉的是中模 blockout 的 30–45 h 中的 20–30 h**，即总工时的 **10–15%**。

不夸张，但也不是没用：起形是最难受的一段，省掉它，剩下的都是"有明确终点的手艺活"。

### 6.3 建议：A 立刻做，B 边做边定

先走 A（1 天）把白盒跑起来，暴露相机锚点、舱门碰撞、枢轴方向这些**只有跑起来才知道的问题**；再决定 B 里的座舱是自做还是外包。理由：A 的 1 天投入会改变 B 的 40–60 小时座舱设计——**因为你会亲眼看到坐在 12.60 m 的高度上、胸甲挡不挡视线**。

## 7 必须先说清的一件事：造型语言

影片截图的造型特征是：**V 形天线 + 双眼缝隙面罩 + 白蓝红三色分割 + 胸甲红色块**。这四件叠在一起，观感与高达系（尤其 RX-78 / RX-0）高度接近。

参赛要求原创（`Docs/Unicorn包导入实测与差距评估.md` §6 已记录该纪律）。V 天线与双眼面罩**单独存在时不构成问题**（是机甲通用语汇），但**四件同时出现**就构成"风格复刻"的印象风险。

建议在几何改造阶段做三处调整，成本很低：

| 特征 | 现状 | 改成 |
|---|---|---|
| 头部天线 | 单根 V 形前伸 | 改为**后掠双片**或**单根后倒鳍**（去掉前伸 V） |
| 面部 | 双眼横向缝隙 | 改为**单条纵向光带**或**三点传感器阵列** |
| 胸甲分块 | 左右红块 + 中央舱门 | 改为**竖向分割**（与舱门方向一致），红色只做缘条 |

三处改动合计 < 4 小时，但把"像高达"降为"是机甲"。**这笔投入的收益比任何贴图都高。**

## 9 glTF 导出器（已完成，2026-11-08）

### 9.1 为什么必须自己写

Blender **自带** glTF 2.0 导入与导出（内置模块 `io_scene_gltf2`，默认启用，不需要装任何插件）。但 Blender 读不了 `mecha_model.py` 里的 Python 对象树——**从 Python 到文件这一步没有任何现成工具能替**。

所以分工是：

```
mecha_model.py（Python 节点树）
      │  ← 这一段必须自己写（本工具）
      ▼
mecha_parts.glb
      │  ← Blender 自带导入器 / Unity + glTFast
      ▼
Blender（Z-up，层级完整）→ FBX 2020 → Unity
```

### 9.2 实现要点

| 要点 | 做法 | 为什么 |
|---|---|---|
| **局部空间顶点** | mesh 顶点用 identity 变换三角化，位置留在节点局部坐标 | 若写世界坐标并把节点变换置空，模型能显示，但**一旋转枢轴整件就绕世界原点飞走** |
| **层级** | `nodes.children` 逐级挂 | OBJ 做不到 |
| **欧拉角** | 由 r3d 的 `Rx@Ry@Rz` 直接算 3×3 再转四元数 | 绕开"欧拉序"歧义，不假设 glTF 用什么约定 |
| **四元数** | Shepperd 分支法，统一取 w ≥ 0 半球 | 任一角稳定，避免上下游符号抖动 |
| **min/max** | 与 float32 顶点逐位一致 | 四舍五入会让声明范围比实际窄，触发 `ACCESSOR_MIN_MISMATCH`（首版实测 180 条 error） |
| **左右命名** | 两种约定都归一成 `_L`/`_R` | 源模型同时存在「同名两次」和「`-1`/`1` 后缀」两种写法（88 个节点） |

### 9.3 产物与验证

| 文件 | 内容 |
|---|---|
| `out/pico/mecha_parts.glb` | 主交付，单文件 533 KB |
| `out/pico/mecha_parts_norm.glb` | 归一化版：H→18.20 m、脚底→y=0（统一缩放 0.9568） |
| `out/pico/mecha_parts_hatch.glb` | 舱门 95° 打开态（244 件） |
| `out/pico/*.gltf` + `*.bin` | 分离式文本版，便于人工核对 |
| `out/pico/*_check.json` | 自检报告 |

**三重验证，全部通过**：

| 验证 | 方法 | 结果 |
|---|---|---|
| 结构 | 重解析 GLB，按层级累乘世界矩阵，**变换真实顶点**后比包围盒 | 与直接测量偏差 **1e-6 m** |
| 规范 | Khronos 官方 `gltf-validator` | 4 个文件全部 **0 error / 0 warning / 0 info** |
| 互操作 | `@gltf-transform/core`（独立第三方实现）读取 | 276 节点 / 242 网格 / 深度 10 / 11 材质，层级完整 |

> 包围盒校验第一版用「局部 AABB 的 8 个角点」变换，得 0.029 m 偏差——那是 AABB-of-AABB 的算法高估，不是导出错误。改用真实顶点后降到 1e-6 m。

### 9.4 与契约的命名对应

导出后左右件已是 `_L`/`_R`，只需一张改名表即可对齐契约：

| glTF 节点 | 契约枢轴 | 实测位置（世界） | 误差 |
|---|---|---|---|
| `elbow_R` | `Pivot_Elbow_R` | (2.360, 11.127, −0.270) | Y 0.07 |
| `wrist_R` | `Pivot_Wrist_R` | (2.524, 8.091, −0.176) | Y 0.09 |
| `hatch_hinge_L/R` | `Pivot_Hatch_L/R` | (±0.570, 12.700, 1.672) | 铰链已实现 ±95° |
| `skirt_front_L/R` 等 | `Pivot_Skirt_*` | — | **不 1:1**：模型每侧两块裙甲，契约每侧一个枢轴，需先合并 |

改名 5 行脚本即可，不需要重做几何。

### 9.5 复跑

```bash
python3 tools/export_gltf.py --hatch      # 开舱：278 节点 / 244 网格
```
