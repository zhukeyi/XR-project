**以下三点必须知道（否则会误判为 bug）：**

1. 合规自检代码里是 **33 条检查定义，实际执行 30–31 条**——两组互斥 + 一条条件输出。看 FAIL 数，不看总行数。
2. 地面探针的高度先验容差是 **0.35 m**，而可用的眼高偏差预算是 **0.220 m**。后者才是硬约束，它是代码扫出来的，不是估的。

## 2. 已修缺陷清单

### 2.1 P0 —— 会导致真机功能失效

| # | 位置 | 问题 | 为什么是 P0 | 修法 |
|---|---|---|---|---|
| 1 | `Core/Spatial/GroundAnchor.cs` | 全流程只用一个眼高常量 `1.15 m` 去算地面探针 | 1.15 m 是**坐姿**眼高（契约「舱地板→SeatAnchor」）。AR 房间尺度下用户站着，真实眼高约 1.65 m，探针会浮在真实地面上方 ≈0.5 m，**超过 0.35 m 高度容差 → 真实地面权重恒为 0 → 平面检测永远 `Unresolved`**，AR 侧 100% 回落到眼高兜底。这不是精度问题，是量纲用错 | 拆成 `seatedEyeHeight` / `standingEyeHeight` 两个字段 + 纯函数 `EyeHeightFor(caps)`：`RoomScale → 1.65 m`，其余 `→ 1.15 m`；探针与日志都用解析后的 `_eyeHeight` |
| 2 | `Core/Inputs/InputSources.cs` → `GazeSource` | `Target` 被赋成相机自身 | `Vector3.Angle(forward, 零向量)` 返回 0，注视角恒为 0，停留计时永不被打断 → **`PanelSelect` 退化成每 `DwellSeconds` 触发一次的定时脉冲**，AR 手势模式下表现为「什么都没看也在乱点」 | 加 `MinTargetDistance = 0.10f` 自指/过近保护 + 一次性告警；`PlatformBootstrap` 不再把 eye 传给 `Target`（S2 由 gameplay 指定真实目标） |
| 3 | `Core/Inputs/InputSources.cs` → `ControllerStickSource` | `Supports` 不含 `Boost` / `PanelSelect` | 这两个通道只有键盘源供给，而**键盘源在 Android 上不产生输入** → 真机上助推（Boost）与面板选择（PanelSelect）**按不出来**。审计报告里「通道有供给者」的判断因此是假阳性 | `Boost ← primaryButton`、`PanelSelect ← secondaryButton`，补进 `Supports` |
| 4 | `Core/Platform/PlatformProfile.cs` + `Editor/PixelRegistrationRecorder.cs` | 像素配准阈值三处不一致：`ToAcceptance()` 硬编码 `1.5`、`Validate()` 用 `> 2f`、Editor 窗口的「上限」字段不落盘 | 出现「窗口显示达标、合规报告说超限」的自相矛盾，且**这个数字是 AR 赛道唯一的量化门槛** | Profile 新增唯一字段 `maxArPixelRegistrationError = 1.5f`；`ToAcceptance` / `Validate` / Recorder 写回三处同源；报错文案带角度换算（不再写死「44 PPD 下 2 px」） |

## 3. 复核通过项（不是缺陷，不要改）

### 3.1 引擎版本口径（原结论已推翻，非笔误）

上一轮的判断「主选 Unity 6.0 LTS，2022.3.62f3 作回退」基于两个**已核实为不成立**的前提：

| 原依据 | 事实 | 判定 |
|---|---|---|
| 「PICO 官方把 6000.0.59f2 写成指定版本」 | 该指定**只属于 Spatial 模式**。PICO 官方表述：XR/OpenXR 模式 **2022.3.15f1+**；Spatial 模式分别列 2022.3.62f2 / 6000.0.59f2。本方案走 OpenXR，2022.3.62f3 已满足下限 | **不成立** |
| 「升级代价不对称，现在装 6 是 1 小时」 | 2022.3 线支持止于 **2025-05-07**，6.0 线止于 **2026-10-16**——**两条线都已 EOL，EOL 不构成差异**。为一条已 EOL 的线重装引擎、重跑 URP 14→17 与 XRI 迁移，只换来「官方在不使用的模式下提过这个版本号」 | **不成立** |

保留的真实理由只有一条但足够：**零安装成本 + 编译门禁同源**。`Tools/compile-check.sh` 用本机 2022.3.62f3 自带的 mono + Roslyn + NetStandard 2.1 做类型完整编译（**不需要 license**），23 个脚本在这一 API 面上 0 error。换版本等于把「已验证」退回「待验证」。

若赛后要长期维护或迁 Vision Pro：目标应是 **6.3 LTS（支持至 2027-12）**，不是已 EOL 的 6.0。

### 3.3 面板落位（12 格全量复算，与代码一致）

用 `HoloPanelLayout` 同一套公式独立手算（可用角已扣 2° 边距）：

| 面板组 | PICO 4（96°×62°，可用 ±46/±29） | AR Studio（43°×28°，可用 ±19.5/±12） | Glasses（23°×20°，可用 ±9.5/±8） |
|---|---|---|---|
| 五块版 | **5 / 5** | **1 / 5**（仅 `hud_center`） | **0 / 5** |
| 三块版 | **3 / 3** | **3 / 3**（`nav_bottom` 16.35°≤19.5 且 11.58°≤12，贴边通过） | **0 / 3**（`hud_center` 横向半宽 12.05° > 9.5°） |

结论「43° 设备上只能减块不能硬压」与「23°×20° 连三块都放不下」均被数据支持。

### 3.4 眼高误差预算 0.220 m（本轮复算）

`EffectiveHeightCutoffMeters()` 的判据是 `SteadyWeight(0.8, 3°, h) < 0.25`，即：

```
0.8 × (1 − SmoothStep(0, 1, h / 0.35)) < 0.25
→ SmoothStep 项 > 0.6875  →  t = h/0.35 > 0.628  →  h > 0.2198
```

扫描步长 0.005 → 首个跌破点 **h = 0.220 m**。因此「眼高假设的误差预算 = 0.220 m」成立，且它比 0.35 m 的容差**更严**——引用容差而非此值时，会低估风险。
